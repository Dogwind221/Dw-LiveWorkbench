# 模块 8：Agent 编排 + Function Calling

> 这一章记录的是**为什么这么做**。代码在 `server/lib/agent/`，
> 接口契约在 [`AGENT-INTERFACE.md`](AGENT-INTERFACE.md)。

## 一、它和模块 7（RAG）到底差在哪

这是整个模块存在的理由，一句话：

| | 模块 7 · RAG | 模块 8 · Agent |
| --- | --- | --- |
| 谁决定流程 | **代码写死**：检索 → 拼 prompt → 生成 | **模型决定**：调哪个工具、调几次、什么顺序 |
| 模型的职责 | 只负责"写" | 负责"决策 + 写" |
| 代码的职责 | 实现流程 | **执行 + 兜底** |
| 能干什么 | 回答问题 | **干活**：出方案、查合规、调数据 |
| 本质 | 让模型**知道得更多** | 让模型**能动手做事** |

**RAG 是 Agent 的一个工具。** 模块 7 的检索能力，在模块 8 里就是 `search_knowledge` 这一个工具。

## 二、Function Calling 的机制（实测确认，不是文档转述）

模型**不能执行任何代码**。它只会生成一段结构化文本：

```json
{"name": "check_compliance", "arguments": "{\"text\":\"老班章能降三高\"}"}
```

真正执行的是我们自己的代码。**Function Calling 的本质是"模型负责决策，代码负责执行"。**

本项目实测的完整闭环（探针脚本，两轮 HTTP 200）：

```
第 1 轮  用户："帮我看看知识库里有多少山头，另外我播过几场？"
         ← 模型返回 content="I'll check both for you." + 2 个 tool_calls
           finish_reason = "tool_calls"（并行调用）
第 2 轮  我们把两个工具的真实结果回传（role:"tool"）
         ← 模型收敛成自然语言，finish_reason = "stop"
```

### 实测踩到的四个坑（都已处理，写下来省后人时间）

| 坑 | 事实 | 处理 |
| --- | --- | --- |
| `arguments` 是**字符串** | 不是对象，要 `JSON.parse`；且可能是 `"null"`、带空格、或坏 JSON | 解析失败给 `args={}` + `argsError`，**不抛异常** |
| **必须禁用思考模式** | 否则：① 强制 `tool_choice` 直接 400；② tool 轮次必须回传 `reasoning_content`，复杂度大增 | 固定加 `thinking:{type:"disabled"}` |
| 工具轮次的 `content` **常常是空串** | 现有 `callApi` 判成功要求 content 非空，会把合法响应判成失败 | 另写 `callApiMessage`，只校验 `message` 存在 |
| `rawMessage` 必须**原样**回传 | 开思考模式时缺 `reasoning_content` 会 400 | 保留原始消息的全部字段 |

## 三、循环层（ReAct）的职责是"可靠的执行器"

`server/lib/agent/loop.mjs` 不实现任何智能，它只做四件事：
**把模型的决定变成真实动作 → 把结果原样喂回 → 在模型失控时硬性刹车 → 记录完整轨迹。**

设计的重心全在**刹车**和**防错**上，因为模型不可信，而它现在有了动手的能力：

| 风险 | 兜底 | 为什么这么设计 |
| --- | --- | --- |
| 死循环烧钱 | `maxSteps`（默认 8）、`maxToolCalls`（默认 12） | 任一超限 → `stopped: true` + 明确 `stopReason`，**不静默截断** |
| 幻觉工具名 | 把错误**连同可用工具清单**一起喂回 | 只说"没这个工具"模型还会瞎试；给出清单它才能走回正轨 |
| 工具抛异常 | 捕获后喂回 | 错误也是对话的一部分 |
| 参数坏 JSON | 喂回解析错误 | 同上 |

这四条合起来是一个原则：**错误也是对话的一部分** —— 模型能看见自己犯的错，才有机会改。

### 一个产品决策：被截断时也要给用户一句话

硬刹车时模型往往还没说话，但**工具已经真的干过活了**。
返回空字符串会让用户以为"什么都没发生"，而实际上可能已经生成了方案。

所以循环层用工具的真实产出兜一句话（内容全部来自工具返回值，**不是编的**）：

> 任务没能在 8 轮内做完（达到循环轮数上限（8 步），已停止），但下面这些已经做完了：
> - search_knowledge：在知识库里找到 5 条相关片段……
>
> 产出文件：output/agent/deck_xxx.json
> 把任务说得更具体一点再试一次，或者告诉我下一步只做哪件事。

## 四、大件产出：工具保持纯函数，编排层负责落盘

`build_live_deck` 生成的完整方案有**上万字**。把它塞进上下文会撑爆 prompt、烧钱、还没用
（模型不需要复述全文）。

所以设计成三层分工：

```
工具        →  只回结构和统计（约 500 字节），同时在 persist 里声明大件数据
编排层      →  真正写盘，把路径作为 savedTo 回传
模型        →  只知道文件名，据此告诉用户"文件存在 X"
```

实测：`build_live_deck` 给模型的 `data` 仅 **524 字节**，而正文 **10916 字**完全没进上下文。

> **踩过的坑**：第一版 `renderToolResult` 只序列化 `{ok, summary, data}`，
> 把 `savedTo` 丢了 —— 结果 `artifacts` 里有路径、模型却不知道文件在哪，
> 落盘这件事对用户等于没发生。**是协作者审出来的，不是我自己发现的。**

## 五、工具描述（description）是唯一的选择依据

模型看不到工具的实现代码，**只能看 description**。所以描述写得准不准，
直接决定它会不会挑对工具。每条必须写清三件事：

1. **做什么**（动宾结构，一句话）
2. **什么时候用**（"当用户问…时用这个"）
3. **返回什么 / 不返回什么**（尤其"不返回全文"这种边界）

反例（禁止）：`"查询知识库"`
正例：`"在普洱茶知识库里检索山头、茶品、合规知识片段。当用户询问某个山头的特征、产地、价格、
冲泡方式，或需要为直播找素材时使用。只返回检索到的原文片段和出处，不会生成新内容。"`

## 六、7 个工具：5 读 + 2 写

| 工具 | 权限 | 干什么 | 底层 |
| --- | --- | --- | --- |
| `search_knowledge` | 读 | 检索知识库（**不生成答案**） | 模块 7 的检索器 |
| `check_compliance` | 读 | 检查话术合规风险，返回违规词 + **可直接替换的说法** | 模块 5 |
| `build_live_deck` | 读* | 生成直播大纲 + 逐字稿（只回结构，正文落盘到 `output/agent/`） | 模块 1 |
| `list_mountains` | 读 | 列出山头 | 模块 2 |
| `get_live_sessions` | 读 | 历史直播场次 | 模块 6 |
| `save_faq` | **写** | 把一条问答存进问答库 | `data/faq.json` |
| `update_deck` | **写** | 改方案的标题 / 时长（**只允许这两个字段**） | `data/decks/*.json` |

\* `build_live_deck` 是纯计算（`buildDeck` 不写盘），落盘由编排层做，所以算读工具。

**读工具直接执行；写工具必须经用户确认。** 下一节讲这个机制。

## 六之二、写操作为什么需要一整套权限层

读工具出错只浪费一次调用；**写工具出错会污染数据，而且往往不可逆**。
直播知识库里多一条错答案，主播上播时会照着念出去 —— 这是业务事故。

而且有三个读操作根本不存在的问题：

| 问题 | 说明 |
| --- | --- |
| **不可逆** | 写错了就写错了，没有 undo |
| **不可信建议** | 模型提议的写入是**基于它自己读到的内容**，它可能读错了、也可能被用户的话诱导了 |
| **重放** | 模型可能同一轮里重复调同一个写工具（实测过它会把读工具连调 3 次，写工具同理） |

### 为什么不能"给工具加个确认参数"

如果由**模型**决定要不要确认，那等于没有权限控制 —— 它可以在参数里写 `confirmed: true` 绕过。
**权限判断必须是代码做的、模型无法伪造的。**

### 两阶段提交

```
第 1 次调用   模型 → save_faq(...)     → 代码【不执行】，生成 actionId，返回待确认卡片
用户确认       看到确切影响（diff + 风险警告）→ 点确认
确认接口      POST /api/agent/confirm → 执行**第一次那份已校验的参数**
```

**`actionId` 是由「工具名 + 规范化参数」算出的确定性哈希**（key 排序后 sha256 取前 16 位）。
这是整个机制的关键：**批准的是"那一份确切内容"，不是"批准这个工具"**。
模型第二次调用时如果改了参数，actionId 就变了，不给执行。

### 我在这里踩的一个真实设计缺陷（值得记住）

第一版把"确认"实现成**带 actionId 重跑一遍 agent**，指望模型重新提出同一份参数。
实测直接翻车：

```
第一次提议：问「老白茶能不能煮着喝」，答「老白茶可以煮，普洱不建议煮」   → actionId A
第二次提议：问「老白茶能不能煮着喝？」，答「老白茶可以煮，普洱不建议煮。」 → actionId B ≠ A
结果：用户点了确认，什么都没发生
```

**模型对同一句话的两次生成不完全一样**（问号有没有、标点全半角），真实用户会 100% 撞上，
而且极难解释。修复方向不是"让模型更稳定"（做不到），而是**确认时根本不再经过模型** ——
直接执行第一次已经校验过、并且给用户看过的那份参数。

> 这就是写操作和读操作最本质的差别：**写操作的流程里不能有第二次模型生成。**

### 其他几条安全设计

| 设计 | 为什么 |
| --- | --- |
| `save_faq` 检查回答里的违禁词并**警告** | 模型可能存进一条"能降三高"，主播照着念就是事故。确认面板必须把风险摆出来 |
| `update_deck` **只允许改 title/durationMin** | 幻灯片、逐字稿、段落结构是联动的，改一个不改另一个会让导出的 PPT 和稿子对不上 |
| `deckId` 用白名单正则 | 模型可能被诱导传 `../../etc/passwd`。黑名单永远漏，白名单更可靠 |
| 原子写（临时文件 + rename） | 写一半进程崩了不能留下坏 JSON |
| 审计日志 `data/agent-audit.jsonl` | 追查"谁批准了什么"时，只有成功记录不够，还要有**被拒的记录** |
| `falseWriteClaim` 检测 | 模型谎称"已保存"但实际没写 —— 这是写操作里最危险的幻觉，必须单独度量 |
| `allowWrites: false` 策略 | 可以整体关闭写能力（比如"只看不写"模式） |

## 七、怎么用

```powershell
cd F:\dsh\直播工作台

# 1. 冒烟（用假模型驱动，不烧 token）—— 88 项断言
node scripts/agent-smoke.mjs

# 2. 冒烟 + 真实模型闭环
node scripts/agent-smoke.mjs --llm

# 3. 行为评测（离线用 stub；不加 --offline 则真实调模型）
node scripts/agent-eval.mjs --offline
node scripts/agent-eval.mjs --repeat=2

# 4. 起工作台，左侧「8 AI 助手（Agent 编排）」
node server/index.mjs
```

HTTP 接口：

```
POST /api/agent/run       {task, maxSteps?}   → {answer, steps, pending, hasWrites, falseWriteClaim, ...}
POST /api/agent/confirm   {actionId}          → 执行已确认的写操作
POST /api/agent/cancel    {actionId}          → 取消，什么都不做
GET  /api/agent/tools                         → 工具清单（带 permission）
GET  /api/agent/pending                       → 当前待确认动作
GET  /api/agent/audit?limit=50                → 权限审计日志
```

HTTP 接口：

```
POST /api/agent/run    {task, maxSteps?}  → {answer, steps, stopped, stopReason, artifacts, meta}
GET  /api/agent/tools                      → 列出可用工具
```

前端面板刻意**把决策过程摊开**：每一步调了什么工具、参数是什么、耗时、成功还是失败。
因为 Agent 出问题基本只出在三处 —— **挑错工具 / 工具返回不对 / 该停不停**。

## 八、评测：Agent 不能测"答案像不像"

RAG 测检索对不对；**Agent 必须测行为对不对**。所以指标是轨迹级的：

| 指标 | 定义 | 门禁 |
| --- | --- | --- |
| `toolSelectionAccuracy` | 该调的工具是否都调了 | ≥ 0.75 |
| `forbidViolations` | 调用了禁止工具的次数（"滥调工具"的直接度量） | **必须 = 0** |
| `crashRate` | 工具报错导致运行失败的比例 | 越低越好 |
| `stepEfficiency` | 实际轮数 / 上限（观察指标，**不是门禁**） | — |
| `stopCorrectness` | 是否自然停止而非撞上限 | — |
| `answerPresent` | 是否有非空答案 | — |

### 离线模式的自我限定（重要）

`--offline` 用 stub 假模型驱动，所以 **`toolSelectionAccuracy` 恒为 1.000** ——
它只证明"循环层把预设轨迹完整执行了、工具层吃下了这些参数"，
**不能证明模型会选对工具**。模型行为**只能看在线模式**。

离线真正有信息量的是**循环自检**（6 项）：硬刹车、工具报错喂回、幻觉工具名自纠、
非法 JSON、并行调用、空响应不死转。这 6 条恰好是"用真实模型撞不出来"的路径 ——
真实模型通常不犯这些错，所以必须用可编程的假模型精确驱动。

### 一个必须承认的评测陷阱：**拒绝**也可能是正确行为

初版把"没调齐期望工具"一律判失败，结果误伤了正确的拒绝。例如：

```
任务：把我这两个月播过的场次调出来，参考最近一场的主题，生成一份 45 分钟方案
实际：只调了 get_live_sessions，然后说明"你这两个月只有 1 场记录，且是复盘场，
      没有可参考的山头或产品信息"，并给出两条可选路径
```

**这是完全正确的行为** —— 真实数据不足以支撑这个要求，模型没有硬编一份方案。
如果把"硬编方案"当成合格，那测的就是幻觉。

所以评测必须支持「**要么调齐工具，要么给出有依据的拒绝**」这一类期望。
**知道什么时候不该干，是 Agent 比"调对工具"更重要的能力。**

### 非确定性

在线模式要调模型，**同一个场景在不同运行间会翻**（实测失败数在 2/19 和 3/19 之间摆动）。
所以在线结果只能报成"**单次观测**"或"**N 次运行的均值与区间**"，
和 RAG 阶段 `citationValidity` 定的规矩一致。**一个会随机翻的场景没有资格当门禁。**
