# 内容生产效率：批量生成 + A/B 对比（第 12 周）

> 前 11 周解决的是"能不能做对"，这一周解决"**做得快不快**"。
>
> 一场直播备货要准备好几个山头的方案和口播稿。一个个点、一遍遍填同样的"目的/受众/风格/时长"，
> 是纯浪费。这一周把这件事从"重复劳动"变成"一次决策"。

---

## 一、批量生成（模块 10）

### 解决什么

选 10 个山头 → 一次出 10 份方案 + 口播稿 + 合规预检。

```js
POST /api/batch
{
  "mountains": ["倚邦", "冰岛", "老班章"],
  "template": { "purpose": "knowledge", "audience": "veteran", "style": "storyteller", "durationMin": 45 }
}
```

返回：

```json
{
  "batchId": "batch_mvdoenpl4c5faa",
  "ms": 228, "total": 3, "ok": 3, "failed": 0, "skipped": 0,
  "results": [
    { "label": "倚邦", "ok": true, "deckId": "deck_...",
      "stats": { "slides": 12, "scriptChars": 8427, "scriptMinutes": 33.5,
                 "complianceLevel": "high", "complianceHigh": 1 } }
  ]
}
```

**实测：3 个山头 228ms** —— 因为生成是**确定性模板引擎，不调模型**，零 token 成本。

### 四个设计决策

**① 顺序执行，不并发（刻意）**

`buildDeck` 是纯 CPU 的模板引擎，不走网络、不调模型。
对它并发只会让 CPU 更忙、上下文切换更多，**并不会更快**。

所以这里刻意顺序执行，只在每项之间用 `setImmediate` 让出事件循环
（否则 50 项会把 HTTP 线程卡住，进度和健康检查都无响应）。

> 将来如果改成 LLM 生成，才需要引入真正的并发控制（限流 / 令牌桶）。
> **现在加一个"看起来并发其实没用"的参数只会误导。**

**② 幂等：输入签名相同就跳过**

每个方案保存时带一个 `inputSignature`（输入内容的确定性哈希）。
重跑同一批时，签名相同的直接跳过：

```
第一次：total 3, ok 3, skipped 0
第二次：total 3, ok 0, skipped 3   ← 全部复用，不产生重复方案
force: true → 强制重跑，生成新的
```

这样"跑一半失败了再跑一次"不会产生一堆重复方案。

**③ 单项失败不拖垮整批**

每项独立 try/catch，失败记进 `results[i].error`，继续跑后面的，最后一起报告。
理由是：批量操作里最烦的就是"跑到第 9 个挂了，前面 8 个白做"。

**④ `dryRun`：先看会生成几份、跳过几份**

界面上的预检用。**注意 dryRun 必须仍然查索引** ——
它存在的意义就是"预览哪些会被跳过"，如果它跳过索引检查，预检就永远说"全都要生成"。

### 边界

| 限制 | 值 | 为什么 |
| --- | --- | --- |
| 单批上限 | 50 项 | 跑太久 + 失败时损失大 |
| 空批次 | 400 `EMPTY_BATCH` | 明确报错，不静默返回空 |
| 不存在的山头 | 降级为"无山场方案"，不报错 | 与 `buildDeck` 的既有行为一致 |

## 二、A/B 对比（模块 11）

### 解决什么

"这个山头该怎么讲？"讲知识科普还是讲山场故事？面对新手还是老茶客？
凭感觉选，选完也不知道差在哪。

用**同一份事实**生成多个变体，给出可比指标，让你**看着数字选**。

```js
POST /api/variants
{
  "base": { "mountainName": "倚邦", "durationMin": 45 },
  "variants": [
    { "label": "知识科普", "overrides": { "purpose": "knowledge", "audience": "veteran", "style": "storyteller" } },
    { "label": "大促逼单", "overrides": { "purpose": "promo", "audience": "regular", "style": "practical" } },
    { "label": "新手入门", "overrides": { "purpose": "knowledge", "audience": "newbie", "style": "warm", "durationMin": 30 } }
  ]
}
```

实测输出：

```
变体      页   字数   口播     计划   密度(字/分)  内容占比   合规
知识科普   12   8595   34.3分   45分      191       76.2%    high(1 高危)
大促逼单   12   8853   35.3分   45分    196.7       78.4%    high(1 高危)
新手入门   11   6164   24.3分   30分    205.5       81.0%    high(1 高危)
```

### 核心设计：**事实锁定**

变体之间只允许改**呈现**（目的 / 受众 / 风格 / 时长），
**绝不允许改事实**（山头 / 茶品 / 价格 / 规格 / 年份）。

为什么这是硬约束：如果 A 方案说 800 元、B 方案说 1200 元，
那这两个不是"两种讲法"，而是**两个不同的商品** —— 拿来对比毫无意义，
而且一旦选错就是**价格事故**。

所以每个变体都算一个 `factSignature`（事实字段的确定性哈希），对比时先校验：

```js
// 正常：只改风格 → 事实锁定通过
{ factLocked: true }

// 有人偷偷改了价格 → 直接拒绝这次对比
{
  factLocked: false,
  warnings: [{
    level: 'error',
    code: 'FACT_CHANGED',
    message: '变体之间的事实字段不一致（价格/规格/商品被改了）。这不是"同一件商品的两种讲法"，而是不同的商品 —— 不要拿来做 A/B 对比，容易变成价格事故。'
  }]
}
```

### 指标怎么读

| 指标 | 含义 | 怎么看 |
| --- | --- | --- |
| **信息密度**（字/分钟） | 计划每分钟讲多少字 | 不同时长只能比这个，不能比绝对字数 |
| **内容占比** | 口播时长 ÷ 计划时长 | 太低=冷场，太高=没互动时间 |
| 页数 | 方案页数 | 结构复杂度 |
| 合规高危数 | 绝对化用语等 | 播出前必须清零 |
| 开场钩子 | 第一句正文 | A/B 最直观的差异往往在第一句 |

### 不假装有"唯一最优"

对比结果给的是**三组提示**，而不是一个"综合评分第一名"：

```json
"guidance": {
  "safest":         { "label": "知识科普", "why": "高危违禁词 1 个、合规分 10" },
  "densest":        { "label": "新手入门", "why": "205.5 字/分钟" },
  "mostInteractive":{ "label": "知识科普", "why": "互动 4.4 分钟" },
  "note": "没有唯一最优：要安全选 safest，要讲透选 densest，要留人选 mostInteractive。按这场直播的目标定。"
}
```

为什么不做综合分：**"最安全"和"信息密度最高"经常不是同一份**。
把真实取舍压成一个数字，是假精确 —— 用户反而更不知道该怎么选。

### 其他自动预警

| 情况 | 预警 |
| --- | --- |
| 变体改了事实 | `error` FACT_CHANGED |
| 计划时长不同 | `info` DURATION_DIFFERS（提示改看密度和占比） |
| 有变体含高危违禁词 | `warn` COMPLIANCE_HIGH（列出是哪几个） |

## 三、测试

```powershell
node scripts/batch-variant-smoke.mjs    # 44 条
```

**全程不调模型**（确定性模板引擎），所以又快又免费 —— 这是"生成不依赖模型"带来的测试红利。

覆盖的关键断言：

```
[A] 批量   ★幂等重跑全部跳过 · force 强制重跑 · dryRun 标出会跳过哪些
           ★静默降级检测（山场没匹配上 / 传错字段名）
           进度回调 · 单项失败不拖垮整批 · 空批/超 50 项边界
[B] A/B    ★改价格 → factLocked=false + error 警告
           ★时长不同 → 提示不可直接比 · 事实指纹与风格无关
           三组决策提示 · "没有唯一最优"说明
[C] HTTP   /api/batch/choices · /api/batch · /api/variants 及各错误码
```

### 静默降级检测（批量场景最该有的一条）

`buildDeck` 对认不出的字段是**忽略**的：传 `mountainId` 而不是 `mountainName`，
它不报错，只生成一份"没有山场信息"的通用方案 —— **看起来完全正常**。

单份生成时这是小问题；**批量 50 份时就是灾难**：50 份都是通用内容，而每一份都"成功"了。

所以批量结果里会显式标出：

```json
{
  "ok": true,
  "degraded": true,
  "warnings": [{ "code": "MOUNTAIN_NOT_FOUND",
                 "message": "山场「xx」在知识库里没匹配到，这份方案是按通用内容生成的" }]
}
```

批次汇总里有 `degraded` 计数 —— **"成功了多少份"和"多少份是真有用的"是两个不同的问题。**

### 产物打 tag，测试可自愈

每个方案可带 `tag`。测试用固定 tag，**开始和结束各清扫一次**。

为什么不能只靠"记下 deckId 再删"：测试进程可能被外部打断
（比如 PowerShell 管道接 `Select-Object -First`，上游会被提前终止），
`finally` 跑不完就会留下垃圾 —— 下次运行第一批会因为"签名已存在"而**全部跳过**，测试直接假失败。

> 这个问题真实发生过：我一度以为是产品 bug，实际是**测试清理不够健壮**。

测试结束会**只删带本次 tag 的产物**，不动用户已有方案（实测：60 份原有方案保留，残留 0）。

## 五、这一周的判断（值得记的）

1. **"不并发"是一个主动决策，不是偷懒。** 纯 CPU 的确定性计算并发没收益，
   加并发只会让代码更难、更难测。
2. **幂等的关键是签名只包含"会影响产出的字段"。** 多塞一个无关字段就破坏跳过逻辑。
3. **A/B 对比最危险的不是"选错"，是"两个变体根本不是同一个商品"。** 所以事实锁定要前置。
4. **不做综合评分。** 把取舍藏进一个分数，比给出三组数据更没用。
