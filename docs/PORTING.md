# 如何把这个工作台移植到你的行业

> 这份文档给想做「咖啡 / 白酒 / 农产品 / 美妆 / 3C」等**直播内容工作台**的人。
>
> 结论先说：**能移植，但不是改一个配置就行。**
> 它现在是「茶行业的一整套产品」，不是「跨行业框架」——但耦合点集中在 **3 个地方**，
> 找对了改起来很快；找不对会改一周还在踩坑。

---

## 一、先判断：你的行业适不适合照搬

这个工作台之所以成立，靠三个前提。**缺一条，架构就得改，不是换数据能解决的。**

| 前提 | 说明 | 自检问题 |
| --- | --- | --- |
| **① 有结构化知识可沉淀** | 茶有山头/茶品这层稳定实体，属性能写下来 | 你的行业有没有"能列成表、且答案相对稳定"的知识？ |
| **② 有话术合规红线** | 广告法 + 平台规则会罚钱 | 说错话会被罚吗？有明确禁用词吗？ |
| **③ 内容生产是重复劳动** | 每场都要出方案、逐字稿、复盘 | 你每次直播要准备几个小时？能模板化吗？ |

**三个都满足** → 可以直接照搬架构。
**只满足 ①** → 建议砍掉合规模块和 Agent，只保留 RAG + 方案生成。
**都不满足** → 这套不适合你，不要硬改。

> 反例：卖标准化 3C 数码——参数页比稿子重要，话术空间小，合规压力主要来自虚假宣传。
> 这种更适合"商品详情自动化"，而不是"直播内容工作台"。

---

## 二、三个配置面（先理解结构，再动手）

```
┌─────────────────────────────────────────────┐
│  领域 schema   ←  你行业有哪些实体、哪些字段  │  data + chunk 映射
├─────────────────────────────────────────────┤
│  模板与话术     ←  方案怎么分段、怎么说      │  deck/build.mjs
├─────────────────────────────────────────────┤
│  领域词表       ←  界面上出现的行业词        │  web/app.js 文案
└─────────────────────────────────────────────┘

真正通用的（一行不用改）：
  检索管道 · Agent 执行器 · 多租户 · 认证 · RBAC · 审计 · 配额
  批量生成 · A/B 对比 · 提词器壳 · 导出
```

**这三面之外的代码，都是和行业无关的。** 这是能被移植的基础。

## 三、分步移植（按这个顺序做，不要跳）

### Step 1｜换知识数据结构（半天）

**文件**：`data/tenants/default/knowledge.json`

现在的结构（茶）：

```json
{
  "regions":   [{ "id": "xishuangbanna", "name": "西双版纳", "cities": ["勐海"] }],
  "mountains": [{ "id": "laobanzhang", "name": "老班章", "region": "西双版纳",
                  "terroir": "…", "treeAge": "…", "priceRange": "…" }],
  "products":  [{ "id": "…", "name": "…", "summary": "…", "sellingPoints": [] }],
  "topics":    [{ "id": "…", "name": "价格体系", "summary": "…", "points": [] }],
  "tags":      [{ "id": "…", "name": "名山头", "desc": "…" }]
}
```

**咖啡的话，最省事的做法是保留结构、只换语义**：

| 茶叶概念 | 咖啡对应 | 直接复用 |
| --- | --- | --- |
| `mountains`（山头） | **产区 / 庄园**（埃塞俄比亚 耶加雪菲、哥伦比亚 慧兰） | ✅ |
| `products`（茶品） | **豆单 / 批次**（水洗耶加 G1） | ✅ |
| `regions`（产区） | **国家 / 大区** | ✅ |
| `topics`（主题） | **知识主题**（处理法、烘焙度、萃取） | ✅ |
| `tags`（人群标签） | **客群标签**（新手/手冲党/意式党） | ✅ |

> **关键技巧**：不要重命名顶层数组。保持 `mountains` / `products` 这两个 key，
> 只在字段内部换含义——这样能省掉一大半改动。

### Step 2｜改字段映射（最核心的一步）

**文件**：`server/lib/rag/chunk.mjs`（第 226–313 行附近）

这里把实体切成检索块，**字段名是写死的**。茶版本的字段清单：

```js
// 山头（mountains）→ 5 个段落
put(terroir, '山场特征', m.terroir);
put(terroir, '产地', m.area);
put(terroir, '海拔', m.altitude);
put(terroir, '树种', m.treeType);
put(terroir, '树龄', m.treeAge);
put(terroir, '土壤', m.soil);
put(tasting, '香气', m.aroma);
put(tasting, '滋味与口感', m.taste);
put(tasting, '汤色', m.soup);
put(price, '参考价格', m.priceRange);
put(price, '避坑要点', m.pitfalls);
put(sale, '卖点话术', m.sellingPoints);
put(sale, '适合人群', m.audience);
put(brew, '冲泡建议', m.brewTips);
```

**咖啡版建议改成：**

```js
// 产区 / 庄园（mountains）
put(terroir, '产地与海拔', m.area);
put(terroir, '处理法', m.process);          // 水洗 / 日晒 / 蜜处理
put(terroir, '品种', m.variety);            // 原生种 / 瑰夏 / 卡杜拉
put(terroir, '风土特征', m.terroir);
put(tasting, '风味描述', m.aroma);          // 花香 / 柑橘 / 莓果
put(tasting, '酸质与醇厚度', m.taste);
put(tasting, '烘焙度', m.roast);
put(price, '参考价格', m.priceRange);
put(price, '避坑要点', m.pitfalls);
put(sale, '卖点话术', m.sellingPoints);
put(brew, '冲煮建议', m.brewTips);          // 水温 / 粉水比 / 研磨度
```

⚠️ **两个必须知道的坑：**

1. **`put(段, '中文标签', 字段值)` 的第三个参数才是数据字段。**
   写成 `m.terrain` 而不是 `m.terroir` 时**不会报错**，数据存进去了但不进检索块——
   表现为"我改了知识库，AI 还是答错"。
2. **一个段落（`newSection()`）会被切成一个块。** 字段越多，块越长，**单个事实越容易被稀释**。
   茶的"山场特征"段有 8 个字段，如果你行业属性少，就把相近的合并、别硬凑。

**改完立刻验证**（不花 token）：

```bash
node -e "import('./server/lib/rag/build.mjs').then(()=>{})"  # 语法自检
node scripts/rag-smoke.mjs     # 28 条断言，会告诉你块数变了没
```

### Step 3｜换合规词库（1 小时，纯数据）

**文件**：`data/tenants/default/compliance.json`（61 KB，三层结构）

```json
{
  "categories": [ { "level": "high", "words": [ … ] } ],   // 精确词
  "patterns":   [ { "level": "mid", "regex": "…" } ],      // 正则
  "contextRules": [ … ]                                     // 语境规则
}
```

**茶行业的红线**：古树/纯料/树龄/"降三高"/"最好的"
**咖啡行业的红线**：保健功效（"提神不伤胃""减肥"）、绝对化（"最好喝"）、产地虚标（"100% 牙买加蓝山"）

> 这块**不用改代码**，换掉 JSON 就行。三层结构可以直接沿用。

### Step 4｜改方案模板（半天到一天）

**文件**：`server/lib/deck/build.mjs`

这里有三处和茶强绑定：

| 位置 | 现在是什么 | 要怎么改 |
| --- | --- | --- |
| 段落角色 | 开场段 / **每款茶**的专属段 / 收尾段 | 换成你行业的结构（咖啡：产区故事 → 风味 → 冲煮 → 价格） |
| `types` 数组 | `['生普','熟普','生茶（散）',…]` | 换成 `['单品豆','拼配豆','挂耳','冷萃']` |
| `topic` 默认值 | `'普洱茶直播'` | 换成你的直播主题名 |

**不要重写整个 build.mjs**。先只改 `types` 和 `topic`，跑一遍看输出，再动段落角色。

### Step 5｜换界面文案（2–4 小时，枯燥但简单）

**文件**：`web/app.js`（约 75 处茶领域词）

关键词：山头、茶品、茶、古树、饼、冲泡、撬茶、生普、熟普

**做法**：先全局搜索列出来 → 一次性替换成你的行业词。
主界面、表单标签、模块副标题、空状态提示都要过一遍。

> 这一步最容易漏：**表单里的 placeholder 和错误提示**也是行业词。

### Step 6｜重做评测集（半天，别省）

**文件**：
- `data/eval/kb-golden.json` — RAG 问答集（茶版 56 题：38 可答 + 18 库外）
- `data/eval/agent-scenarios.json` — Agent 场景（茶版 31 条）
- `data/eval/_chunk-ids.json` — 块 ID 快照（改动后会不一致，需重建）

**为什么必须做**：没有评测集，你改了字段根本不知道召回有没有变差。
建议照抄比例：**70% 库内题 + 30% 库外题**（库外题用来验拒答，最容易被忽略）。

```bash
node scripts/rag-eval.mjs --offline    # 出 recall@5 / MRR
```

**茶版基线**：recall@5 = 0.974 / MRR = 0.762。你的行业做到 **0.85 以上**就算可用。

## 四、总工作量估算

| 你的目标 | 要做的步骤 | 时间 |
| --- | --- | --- |
| 换个行业**自己用** | Step 1–4（跳过 5、6 也能跑，但体验差） | **1–2 天** |
| 换个行业**给别人用** | 1–6 + 英文文档 + 示例 domain | **2–3 周** |
| 做成**多行业平台** | 额外做领域配置抽象（见第五节） | 数月 |

## 五、如果你想做成真正的"跨行业基底"

现在缺的不是代码量，而是**三个配置面没有外置**。要做的改造：

### 5.1 抽出 `domain.json`

把 `chunk.mjs` 里写死的字段清单变成配置：

```json
{
  "entityLabel": "产区",
  "sections": [
    {
      "name": "风土",
      "fields": [
        { "key": "area", "label": "产地与海拔" },
        { "key": "process", "label": "处理法" },
        { "key": "variety", "label": "品种" }
      ]
    }
  ]
}
```

`chunk.mjs` 改成遍历 `sections` → `fields` 生成块。**这一步做完，换行业 = 换一份 JSON。**

### 5.2 模板目录化

```
domains/tea/     { domain.json, compliance.json, knowledge.json, templates/ }
domains/coffee/  { … }
```

`deck/build.mjs` 从 `domains/<当前租户>/templates/` 加载段落结构。

### 5.3 UI 词表

把 `web/app.js` 里的 75 处行业词收敛成一份 `terms.json`，运行时按 domain 取。

> **判断标准**：如果改这三个配置就能跑新行业，那才算"基底"；
> 如果还要动 `chunk.mjs` 的代码，那就还是"产品"。

## 七、验收清单（改完逐条打勾）

- [ ] `node scripts/smoke.mjs` 全过
- [ ] `node scripts/rag-smoke.mjs` 全过（块数和你预期一致）
- [ ] `node scripts/rag-eval.mjs --offline` 跑出 recall@5 ≥ 0.85
- [ ] 用你行业的一个真实问题问 RAG，**每句话都能点回出处**
- [ ] 问一个你行业里**库里没有**的问题，它明确说"不知道"而不是编
- [ ] 合规检查能命中你行业的 2–3 个典型违规说法
- [ ] 生成一份方案，逐字稿能直接念（有停顿提示、不像模板）
- [ ] 界面上**没有残留的茶行业词**

## 八、几件别做的事

| ❌ 别做 | 为什么 |
| --- | --- |
| 一上来就重写 chunk.mjs | 先跑通 Step 1–3，确认 RAG 能出结果，再动 |
| 直接把 `mountains` 重命名成 `origins` | 会连带改几十处，收益为零。**保留 key，换语义**更省 |
| 保留茶的合规词库 | 你会既漏掉你行业的红线，又误杀正常话术 |
| 跳过评测集 | 没有 baseline，你无法判断改动是变好还是变坏 |
| 一上来就做多行业抽象 | 先让一个行业跑通，再抽象。这是两次不同的工作 |

## 九、一个诚实的提醒

这套东西的价值 **不在代码，在"某个行业的一整套流程理解"**。

代码部分（检索、Agent、多租户）大约 1–2 个月能重写一份；
但"茶直播到底该怎么分段、哪些话术会违规、主播真正常问什么"——这部分抄不走。

所以移植的时候，**最花时间的不是改代码，是把你行业的知识整理成结构化数据**。
按经验，那部分占整个移植工作量的 **60–70%**。
